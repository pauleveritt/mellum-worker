## How to read an entry

Each idea follows the Learning Center's six-step template: Problem → Eval
case → Evidence of the problem → Solution → Evidence it worked →
Interpretation. Steps 1–5 carry one badge each; Interpretation carries none.

| badge | meaning here |
| --- | --- |
| `reference-run` | a preregistered Ollama run recorded in `evals/` (none exist yet) |
| `cited` | an existing oMLX or mlx-lm record in `evals/` or a research note on `main` |
| `screen` | a few targeted runs or one observation, not preregistered, or with no record |
| `conjecture` | no run behind it: reasoning, design or unit tests only |

For steps 1, 2 and 4 the badge is the strongest evidence the statement rests
on; for steps 3 and 5 it is the strength of the evidence itself. Each
Interpretation names the weakest badge it relies on and claims no more.

## Idea 1: the worker decides when it is done

| step | content | badge |
| --- | --- | --- |
| 1. Problem | The worker writes its own test from the spec's `Tests:` line, which omits Phase 4's `id` requirement; that test passes and the worker stops. A21: "Every failing run passed its own test command." | `cited` |
| 2. Eval case | Rung 9 (AgentClinic Phase 4), scored by `check_agentclinic`: visible tests and the hidden oracle pass, existing tests unedited, no writes outside the allowed paths. | `cited` |
| 3. Evidence of the problem | A21 rung 9 0/3 on oMLX, all three the id miss; the rung 9 screen ties the miss to the one-file roadmap (5 of 6 against 1 of 6). PR #1's stock arm A: rung 9 0/3 on `mlx_lm.server`, no record. | `cited` |
| 4. Solution | `--acceptance-test` (`5bf4a0d`, `ff17d60`): place an external, complete test the worker did not write and cannot edit. Principle in `2026-10-18-harness-exit-gate.md`: the oracle must be external, complete and unweakenable. | `screen` |
| 5. Evidence it worked | One scored rung 9 PASS (20 turns, 194 s) against one stock FAIL, on `mlx_lm.server` (`2026-10-18-mediated-rung9-screen.md`). The run also had the no-servers line (idea 7) and an unused re-dispatch budget. | `screen` |

**Interpretation (draft).** The problem is well measured: two records on the
shipped backend show the worker passing its own incomplete test. The fix
rests on one confounded screen (weakest badge: `screen`): n = 1, a different
server, and two other changes in the same run. It says the mechanism can
reach a hidden-oracle pass, not that it raises a rate. Open: arm B of the
preregistered run, then an oMLX or Ollama reference run.

## Idea 2: a fixed test alone does not reach green

| step | content | badge |
| --- | --- | --- |
| 1. Problem | Given an external, complete test, the worker added the missing `id` field but its code did not collect, and the loop ended there. | `screen` |
| 2. Eval case | Phase 4 driven by hand through the tool loop, outside Pi and the ladder. | `screen` |
| 3. Evidence of the problem | One hand-driven probe: oracle redirected the worker, neither the test nor the hidden oracle reached green (`2026-10-18-harness-exit-gate.md`). | `screen` |
| 4. Solution | `--redispatch N` (`6426b2b`): after each stop, re-run the frozen test and hand its failure to a fresh worker. | `screen` |
| 5. Evidence it worked | The same probe with freeze, re-dispatch and a larger per-turn budget converged at turn 25, hidden oracle green (n = 1). In idea 1's scored PASS no re-dispatch fired. | `screen` |

**Interpretation (draft).** "Redirection is necessary, not sufficient" is the
note's own conclusion, and it rests on two hand-driven runs (weakest badge:
`screen`). Three things changed between them (freeze, re-dispatch, budget),
so the lesson can show the shape of the loop, not which part closed the gap.
The scored ladder has not yet exercised a re-dispatch that mattered.

## Idea 3: a greedy retry repeats itself

| step | content | badge |
| --- | --- | --- |
| 1. Problem | At temperature 0 a retry re-runs the same decode and produces the same output. | `conjecture` |
| 2. Eval case | None. | `conjecture` |
| 3. Evidence of the problem | Reasoning only (`LESSONS.md` 32). | `conjecture` |
| 4. Solution | `aa5f6f3`, `3eddfb9`: each retry raises temperature by 0.25 up to a 0.5 cap and moves the seed; past the cap only the seed moves. | `conjecture` |
| 5. Evidence it worked | The ramp was seen firing (temperature 0.2, seed 43). The cap rests on one run where a 0→1.0 ramp gave 44 tool errors in 121 requests; no record. Nothing shows a retry passing because of the ramp. | `screen` |

**Interpretation (draft).** Plausible and cheap, but unmeasured (weakest
badge: `conjecture`). The one observation is about the cap: too hot breaks
JSON tool calls. A lesson can teach the trade-off; it cannot claim a lift.

## Idea 4: a timeout ends the loop

| step | content | badge |
| --- | --- | --- |
| 1. Problem | A worker that stalls until its deadline ended the re-dispatch loop, so on a slow backend no retry ever fired (`107b480`). | `screen` |
| 2. Eval case | Rungs 6 and 8, where deadline hits occur. | `cited` |
| 3. Evidence of the problem | Deadline hits on oMLX: A21 control rung 6 r2 and rung 8 r1. Stock arm A on `mlx_lm.server` lost rungs 6 and 8 to deadlines (no record). | `cited` |
| 4. Solution | Treat a timeout as a failing frozen test and re-dispatch a fresh worker on the same workspace ("small deadline slicing"). | `conjecture` |
| 5. Evidence it worked | None beyond unit tests. | `conjecture` |

**Interpretation (draft).** That deadlines cost passes is recorded; that
slicing recovers them is not (weakest badge: `conjecture`). Bounded cost is
`(N+1) × deadline`, so the lesson must state the cost along with any gain.

| step | content | badge |

both calls and results. A good first findings lesson for a negative result.
