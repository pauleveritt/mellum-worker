# Plan-mode delegation — medium n=3 (preregistered)

**What is measured:** the plan-mode delegation loop
(`MELLUM_DELEGATE_PLAN=1` + `preset:medium`) run three times on the medium
suite, scored by the suite's hidden oracle (18 checks). **What is conjecture:**
that the simple no-tests loop holds its single-run lead (18/18) over the
test-heavy step-file loop across repeats.

## Provenance

These runs exercise the **real shipped extension**
(`extensions/mellum-worker.ts`, the `PLAN` branch), the **real local model**
(Mellum Q4_K_M via llama-server on `:8001`), and the **real hidden grader**
(`learn/code/suites/medium/grader`). They are driven directly through `pi -p`
from a scratchpad driver, **not** through `run_ladder` — so this is a repeated
screen of the shipped loop, not a ladder-recorded result. A ladder-recorded
result would need the plan arm wired into `run_ladder`; that is follow-up.

## Preregistration (fixed before the runs)

- **Arm:** plan-mode delegation — the architect splits the spec into
  `stepNN.md` docs with the requirement text copied verbatim and **no
  per-step tests**; a fresh worker builds each step in order; there is no
  per-step gate. Workers load `preset:medium` remedy units. Primary backend
  (local Q4 on `:8001`).
- **n:** 3 fresh runs, each from a clean `suites/medium/base` seed, each in its
  own workspace.
- **Tier:** medium only. Easy is saturated — both the step-file arm and plan
  mode already score 4/4 — so easy has no power to discriminate the arms.
- **Scoring:** the hidden oracle, 18 checks across `test_phase1..4`. Per-run
  score is the pass count; also record the per-phase split.
- **Comparators (historical, n=1, not re-run here):** step-file + remedies
  **13/18**; per-phase **6/18**. See
  [delegation-vs-remedies](2026-11-03-delegation-vs-remedies.md).
- **Decision rule, fixed in advance:** report the **median and range** of the
  3 scores. Plan mode is adopted as the medium default if its median ≥ 13 (the
  step-file lead) **and** no run falls below 6 (the per-phase floor).
  Otherwise the single 18/18 is treated as variance and the step-file arm
  stands. Whatever the outcome, state it as a **3-run screen of the shipped
  loop**, not a ladder result — a small-n result, labelled as such.

## Results

Three fresh runs, hidden oracle (18 checks), per-phase split. The combined
`pytest grader_tests` run **aborts on a collection error** (an `Interrupted`
session reports 0 passed), so the accurate 18-check score is the **sum of the
four per-phase files run separately** — that is what is recorded here.

| run | steps built | p1 (4) | p2 (6) | p3 (3) | p4 (5) | **score** | wall |
|-----|-------------|--------|--------|--------|--------|-----------|------|
| rep1 | 4  | 4 | 0 (err) | 3 | 0 (err) | **7/18**  | 571s |
| rep2 | 13 | 4 | 6 | 3 | 2 | **15/18** | 1631s |
| rep3 | 15 | 4 | 5 | 3 | 5 | **17/18** | 1381s |

**median = 15/18 · range 7–17 · mean 13.0.**

rep1 is a genuine broken build, not a grading artifact: its architect
under-split the spec into only 4 coarse steps and never created the
module-level `complaints` collection the spec (and the oracle's `_seed.py`)
require, so the phase-2 and phase-4 grader files error at collection. The guard
added this session (retry a truncated architect) prevents the **zero-docs**
collapse that voided the first attempt of this screen; it does **not** catch an
architect that writes docs but splits too coarsely — a separate variance mode,
newly surfaced here.

Comparators (n=1, historical): step-file + remedies **13/18**, per-phase
**6/18**.

## Decision

By the preregistered rule — adopt if median ≥ 13 **and** no run below 6 — plan
mode **is adopted as the medium default**: median 15/18 ≥ 13, floor 7/18 ≥ 6.
It leads the step-file arm's single 13/18 on the median while dropping all the
per-step test machinery. This is a **screen-level result**: three runs of the
shipped loop driven directly through `pi -p`, not a `run_ladder`-recorded rate,
and the comparator is itself n=1. Treat it as the lead it is.

The adoption carries a **variance caveat**: one run in three collapsed to a
broken build when the architect split too coarsely. The per-step gate that the
step-file arm pays for is exactly what would have caught rep1's missing
contract. So the honest reading is: plan mode wins on the median and is the
simpler default, but it is higher-variance, and closing the coarse-split mode
(a floor on step count, or a lightweight contract check) is the next lead.

## What would falsify this / Risks

- A run that collapses low (a phase missed entirely) would show the no-gate
  loop is high-variance — the per-step test gate it drops may be load-bearing
  on a bad draft, even if the median is high.
- The architect's step granularity varies run to run (22 steps in the screen);
  very different splits across reps would mean the arm is really two arms.
- n=3 is small. A median is a screen, not a rate; the ladder wiring is what
  turns this into a recorded result.
