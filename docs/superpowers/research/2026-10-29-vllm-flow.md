# The full spec flow on the vLLM baseline host

**What is measured.** One run per level (n = 1) of `learn/code/flow_run.py`
in forced mode on 2026-10-28/29, against the pinned vLLM baseline host (RTX
A6000, Mellum 2.1 BF16, vLLM 0.32.0, Pi 1.3.0), commit `fdcab52`. Hidden
grades: Bronze 4/4 (a full pass), Silver 13/18, Gold 30/34. Every gate
fault below was reproduced by re-running the frozen gate against the
workspace by hand. Record:
[`evals/2026-10-29-vllm-flow/`](../../ladder/2026-10-29-vllm-flow/README.md).

**What is conjecture.** Any rate, and any comparison with the baseline's pass
counts (n = 3, the `bare` arm): this is one run, and its unit is checks
passed, not sessions passed. That the gate fixes below would have changed
Silver's grade: they are untested on a live model.

## Why run it

The baseline measured Pi and the model alone (Bronze 1/3, Silver 1/3, Gold
0/3 sessions passing). The question was whether the spec-driven flow, with
its planner, examiner, frozen per-phase gates and git checkpoints, passes
all three levels on the same host.

It does not, but it gets far: Bronze passes, and Gold reaches phase 7 of 7
with 30 of 34 hidden checks, further than any setup recorded so far.

## Getting it to run

Three harness bugs stopped the first attempt before the model was called,
and two more in the box tooling cost two rentals. All are fixed with tests
shown failing first:

- `35bcce9`: a relative `--runs-dir` resolved the recorder and Pi profile
  inside the workspace ("Unknown provider"); the final grade unpacked three
  of four return values, then subtracted a list from an int.
- `ff0e90a`: `serve`'s `pgrep -f 'vllm serve'` matched its own command line,
  so vLLM was never started.
- `fdcab52`: vLLM 0.32 renames its process, so a name match called a live
  server dead; vLLM is now tracked by the PID `serve.sh` execs into.

## Results

| Level | Phases passed (gate) | Hidden checks | Missed |
| --- | --- | --- | --- |
| Bronze | 1/1, in round 5 | 4/4 | none |
| Silver | 4/4, phase 4 in round 6 | 13/18 | all five phase 4 checks |
| Gold | 6/7, phase 7 failed 6 rounds | 30/34 | four migration checks |

Gold's misses are the model's: its `add_tickets_note` migration is invalid
SQL (`near "WHERE": syntax error`) and stayed so for six rounds. The phase 5
gate (the audit trail missing an `add` entry) and the phase 7 gate failed
for real gaps in the build. Silver's and Bronze's are not.

## Three gate faults

**A gate test that cannot pass.** Bronze's gate called
`inspect.getfile(app)` on a FastAPI instance, which raises `TypeError` for
every app. Silver's phase 4 gate posted a complaint without
`follow_redirects=False` on a redirect-following client, then asserted 303;
the app answered 303 exactly as the spec says. Bronze got through in round 5
only by monkeypatching `inspect.getfile` at the top of `app.py`: gaming the
gate, harmless here because the hidden grader passed it independently.

**A revert deletes the frozen gate.** Round 5 of Silver's phase 4 left
`app.py` uncompilable, and the harness reverted to the phase 3 checkpoint.
The phase 4 gate was frozen after that checkpoint, so the revert removed it.

**A re-frozen gate drops the phase's requirement.** Round 6 froze a new phase
4 gate with two tests (the board loads; posting redirects). Neither touches
resolve or reopen. The phase passed and was checkpointed with no resolve or
reopen code in `app.py`; the hidden grader missed all five phase 4 checks.
This is the weak-gate-passes-a-wrong-build case the exit-gate note warns
about, created by the harness's own revert.

## Decision

Fix the three as harness guarantees, agnostic of any suite, before the next
flow run: (1) a frozen gate survives a revert; (2) once a phase has a frozen
gate, it is never replaced; (3) a gate whose tests error rather than assert
against the workspace is not frozen. Each is a property of the harness, not
a prompt rule, per `AGENTS.md`.

*2026-10-29, landed.* (1) and (2): `7b70a60` keeps every frozen gate across a
revert. The extension already refuses a second `examine` while the phase's
gate file exists, so with the file kept, no weaker gate can replace it. (3):
only its observed instance, `9b79a32`, which forces every gate `TestClient` to
`follow_redirects=False`. The general dry run is the BACKLOG entry "Reject a
gate test that cannot pass". None of this is verified on a live model yet.

## What would falsify this

- A rerun at the same commit where Silver's phase 4 gate is never re-frozen
  after a revert would mean the second and third faults are rarer than this
  run suggests; the fix still holds as a guarantee.
- A gate test that errors on a correct app for a reason the dry run cannot
  see (an import-time side effect, say) would mean fix (3) is incomplete.

## Risks

- n = 1 per level. Gold's 30/34 may not repeat; Bronze's pass came after a
  monkeypatch that a stricter review would reject.
- Fix (3) can reject a gate the model could have satisfied by building more
  (an `ImportError` because a module does not exist yet). It must treat a
  missing module as "not built yet", not as a broken test.
- The vLLM log for this box was not confirmed fetched; server-side errors, if
  any, are not in the record.

## Rerun with the fixes (2026-10-29)

Same flow at `6985a6e`, the three levels concurrently on one host, n = 1:
**Bronze 4/4 and Silver 18/18 (both full passes), Gold 30/34**
([record](../../ladder/2026-10-29-vllm-flow-rerun/README.md)). Every Bronze
and Silver phase passed its gate in round 1 with no revert, so the revert fix
was not exercised there and the passes are not attributable to it; no
`inspect` patch appeared. In Gold phase 7 a round left the app uncompilable,
the harness reverted to the phase 6 checkpoint, and the uncommitted
`phase_7.py` gate survived: the revert fix working live. Gold missed two
migration and two visits-report checks. Its phase 5 gate failed six rounds on
a self-contradicting test (four state changes, then an assertion of three
audit entries): a broken gate that raises no exception, so the dry run in the
BACKLOG entry would not catch it.
